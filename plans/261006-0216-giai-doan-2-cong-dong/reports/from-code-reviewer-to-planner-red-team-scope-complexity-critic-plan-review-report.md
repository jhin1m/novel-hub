## Finding 1: Phases 8 and 9 log new moderation actions through a type that is pinned 1:1 to the one-click action schema
- **Severity:** High
- **Location:** Phase 8, "Requirements" (`feature_story`/`unfeature_story`); Phase 9, "Requirements" (`create_contest`/`update_contest`/`set_contest_placement`, target_type `contest`); Phases 1/4 "Related Code Files" (targets `comment`/`rating`)
- **Flaw:** `logModerationAction(tx, actor, target: ModerationTarget, action: ModerationAction, note)` (`packages/core/src/moderation/log-action.ts:14-19`). `ModerationAction` is derived from `MODERATION_ACTIONS` (`shared/src/schemas/reports.ts:28-41`), which is documented as "One-click moderator actions; also the `moderation_actions.action` values". That list is locked to `moderationActionSchema` bodies by `reports.test.ts:58` (`expect(bodies.map(b => b.action)).toEqual([...MODERATION_ACTIONS])`), and `ACTION_LABELS: Record<ModerationAction, () => string>` (`apps/web/src/components/moderation/report-actions.ts:5`) must cover every member. `ModerationTarget.type` is `'story'|'chapter'|'user'|'tag'|'report'` (`log-action.ts:9`), with no `comment`, `rating` or `contest`. Phases 8 and 9 list none of `reports.ts`, `reports.test.ts`, `log-action.ts`, `report-actions.ts`. Phases 1 and 4 also omit `log-action.ts`.
- **Failure scenario:** The Phase 8 cook adds `feature_story` to `MODERATION_ACTIONS`. `ACTION_LABELS` then fails typecheck, and once it gets a label, `reports.test.ts:58` fails because there is no schema body for it. The cook either adds a fake `feature_story` body to `moderationActionSchema`, which exposes it on `POST /moderation/actions` with a dispatch that has no case and hits `never`, or casts the string. Either way the "one-click action" invariant breaks. Phase 9 hits the same problem a second time and also needs `'contest'` in `ModerationTarget`.
- **Evidence:** `log-action.ts:8-19`; `reports.ts:27-41,92-109`; `reports.test.ts:43-62`; `report-actions.ts:5-17`; `apply-action.ts:12-40` (dispatch switch).
- **Suggested fix:** In Phase 1, split the contract: keep `MODERATION_ACTIONS` for card actions and add `MODERATION_LOG_ACTIONS = [...MODERATION_ACTIONS, 'feature_story', 'unfeature_story', 'create_contest', 'update_contest', 'set_contest_placement'] as const`, used only by `logModerationAction`. Widen `ModerationTarget.type` once in Phase 1 to cover `comment`, `rating`, `contest`. Add `log-action.ts`, `reports.ts` and `reports.test.ts` to the file tables of Phases 1, 4, 8 and 9.

## Finding 2: Phase 4 adds denormalized rating totals that nothing needs, and they disagree with the distribution by design
- **Severity:** High
- **Location:** Phase 4, "Key Insights", "Non-functional", "Implementation Steps" step 3, "Dependency Map"
- **Flaw:** The plan adds `stories.rating_count` and `stories.rating_sum`, a `SELECT … FOR UPDATE` on `stories` in every rating write, a shared `adjustRatingTotals`, delta logic for create, edit, edit-while-hidden, hide, restore and delete, a backfill migration and a concurrency int test. Yet the plan says (a) the score is never rendered into SSR (plan.md:55), (b) "không phase nào trong plan này cần" these columns (phase-04:113), and (c) the distribution already runs a `GROUP BY score` that filters banned users (phase-04:44,92), so `count` and `sum` come free from those same 5 rows. The plan even writes down the inconsistency it creates: "summary lấy count/sum từ cột tổng … distribution lọc banned → có thể lệch nhẹ" (phase-04:93).
- **Failure scenario:** A reviewer gets banned. The header shows "4.2 · 10 lượt" while the bars add up to 9. A mod hides a review while the user is editing it. That is the "sửa khi ẩn" branch, the place most likely to drift, and it permanently corrupts the counter with no recompute job (the plan rejected the research's recompute job, plan.md:96). Every rating write also contends with the `stories` row lock that publish and moderation already take (`publish-chapter.ts:46` path, `content-visibility.ts`).
- **Evidence:** `packages/db/src/schema/community.ts:64-81` (`ratings_story_id_idx` already exists); `packages/db/src/schema/stories.ts:37-73` (no rating columns); phase-04 lines 26, 42, 92-93, 113, 132-133.
- **Suggested fix:** Drop `rating_count`, `rating_sum`, `adjustRatingTotals`, the `FOR UPDATE` and the backfill. Build the summary with one query: `select score, count(*) from ratings join users … where story_id=$1 and status='visible' and u.status<>'banned' group by score`, then derive count, average and distribution from it. Add the columns later only if story cards ever need the average. Keep `ratings.id`, `status` and `updated_at`, which the report target and edit flow do need.

## Finding 3: Phase 2 injects UI into the chapter text, against spec §8, and turns every mid-screen tap into a "+" prompt
- **Severity:** High
- **Location:** Phase 2, "Overview", "Requirements" (bong bóng/"+"), "Architecture" (`useParagraphAnchors`, portals), "Risk Assessment"
- **Flaw:** Spec §8 (docs/project-spec.md:269) says "Không chèn gì vào giữa nội dung". Phase 2 cites that line in its Context Links, then inserts a `<span data-pc-anchor>` plus a portal button into every `<p data-pid>` inside a `dangerouslySetInnerHTML` subtree. It persists count bubbles and adds a tap-to-select "+" on every paragraph. A tap in the middle third is the existing gesture for toggling the reading bar (`use-nav-visibility.ts:40-47`). With this design every such tap also selects a paragraph and shows "+", which the plan accepts ("hai hành vi độc lập", phase-02:129). This is the most fragile UI in the plan: React-unmanaged DOM mutation, anchor lifecycle tied to `html`, `contentRef` progress measurement (`chapter-content.tsx:19,26`, used by `useReadingProgress`) now measuring injected nodes, plus orphan logic. And the plan admits keyboard users cannot reach "+" (phase-02:128).
- **Failure scenario:** A reader taps mid-screen to bring back the bar and "+" appears inline in the text on every tap. Bubbles reflow lines on narrow screens despite the "no layout shift" claim, because an inline element at the end of a paragraph can wrap to a new line. The spec owner sees content insertion the spec explicitly forbids. Per CLAUDE.md ("Spec mâu thuẫn … theo spec; spec thiếu hoặc mơ hồ thì hỏi"), this should have been a question, not an `[auto]` decision.
- **Evidence:** docs/project-spec.md:269; `apps/web/src/components/reader/chapter-content.tsx:25-26`; `apps/web/src/lib/reader/use-nav-visibility.ts:40-47`; phase-02 lines 20, 36, 42, 128-130.
- **Suggested fix:** Escalate to the user as an open question. Propose an MVP that inserts nothing into the text: (a) selecting text or long-pressing a paragraph opens a sheet scoped to that paragraph, and (b) per-paragraph counts appear as a list inside the end-of-chapter comment area ("Đoạn 12 · 3 bình luận" → scrolls to the paragraph and opens the sheet). Drop the persistent bubbles, `useParagraphAnchors` and the portals. Keep `paragraph_id` validation, the orphan rule and `GET paragraph-counts`.

## Finding 10: Phase 1 and Phase 4 report targets break the "public keys only" report contract without saying so, and the plan names the field two ways
- **Severity:** Medium
- **Location:** Phase 1, "Architecture" (`ReportButton target {type:'comment', id}`) vs "Related Code Files" (`target comment {commentId}`), "DTO … id comment là UUID"; Phase 4, "Requirements" (target `rating` = id đánh giá)
- **Flaw:** The existing contract is explicit: `reportTargetSchema` is "by public keys only (internal ids never leave the server)" (`shared/src/schemas/reports.ts:49`), `ReportDto` notes "`reportId` is the only internal id" (`core/src/reports/list-reports.ts:32`), and `reports.test.ts:21-27` has a case titled "rejects internal ids" that includes `{type:'comment', id}`. The plan sends raw UUIDv7 comment and rating ids to clients and accepts them as report targets. The practical risk is low, since UUIDv7 leaks creation time, which is shown anyway. The real problem is that the plan does not acknowledge it is breaking a documented invariant, and it gives two different shapes (`id` vs `commentId`) for the same target.
- **Failure scenario:** The cook picks `{type:'comment', id}` from the Architecture block. The existing "rejects internal ids" test then fails, because that exact body now parses. The cook "fixes" it by deleting the case, and the reason behind the invariant is lost without review.
- **Evidence:** `packages/shared/src/schemas/reports.ts:49-54`; `packages/shared/src/schemas/reports.test.ts:21-27`; `packages/core/src/reports/list-reports.ts:32`; phase-01 lines 54, 63, 72; phase-04 line 38.
- **Suggested fix:** Record the decision in plan.md: comments and ratings have no natural public key, so their UUID is the public key. Fix one shape (`{type:'comment', commentId}`, `{type:'rating', ratingId}`), update the doc comments in `reports.ts:49` and `list-reports.ts:32`, and rewrite the test case so it still rejects `storyId` and the bare `id` form.
