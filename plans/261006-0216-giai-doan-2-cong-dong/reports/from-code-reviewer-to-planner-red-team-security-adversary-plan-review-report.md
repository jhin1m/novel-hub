# Red-team plan review: Security Adversary + Fact Checker

Plan: `plans/261006-0216-giai-doan-2-cong-dong/` (plan.md, phase-01..09). Codebase verified by grep/read on 2026-10-06.

Fact-check summary: most cited paths/symbols exist (`findReadableChapterRef`, `publicStoryWhere`, `isStoryPubliclyVisible`, `parseStoryKey`, `isValidPid`, `slugify`, `canonicalPath`, `QUEUE_PREFIX`, `registerPublishingSchedulers`, `routeContentJob`, `uuidv7()` default, rate limit `comment` at `rate-limits.ts:92-99`). Line drift is trivial (`community.ts` comments 36-62, notifications 85-100). CSRF is already global (`packages/api/src/app.ts:20`, `middleware/csrf.ts:15-31`), so new mutating routes are covered. Real gaps are below.

## Finding 1: Comment/rating moderation skips the self-dealing and hierarchy guards
- **Severity:** High
- **Location:** Phase 1, "Implementation Steps" step 4 (`setCommentHidden`, `resolveVisibleTarget`); Phase 4, "Implementation Steps" step 4 (`setRatingHidden`); Phase 8/9 "Requirements" (mod create featured slot / set placement)
- **Flaw:** Existing moderation stops a mod from acting on their own content or on content by a user they can't moderate. It does this through `canModerateUser(actor, author)` in `content-visibility.ts` and `targetOwnerId()` in `resolve-reports.ts`. `targetOwnerId` only knows `user|story|chapter` and returns `null` for any other type. The plan adds `comment` and `rating` targets without extending `targetOwnerId` and without requiring `canModerateUser` in `setCommentHidden`/`setRatingHidden`. Phase 8/9 also let a mod feature their own story or award their own story 1st place.
- **Failure scenario:** A mod posts an abusive comment or a rating-bomb review. Users report it, and the mod dismisses the reports (`closeReport` sees owner `null`, not `actor.id`) or restores their own hidden comment. A mod can also hide an admin's comments, which `canModerateUser` forbids for stories. And a mod can put their own story in `home_hero` for 90 days or give it contest placement 1.
- **Evidence:** `packages/core/src/moderation/resolve-reports.ts:8-26` (`targetOwnerId` returns null for unknown types), `:51-53` (self-close check depends on it), `:67-73` (`isOwnReport`); `packages/core/src/moderation/content-visibility.ts:35-36` (`canModerateUser` guard on story/chapter); `packages/core/src/moderation/apply-action.ts:79`; `packages/core/src/policies/moderation.ts:29-42`.
- **Suggested fix:** Phase 1/4: extend `targetOwnerId` with `comment` → `comments.user_id` and `rating` → `ratings.user_id`. Require `canModerateUser(actor, {id: author, role})` in `setCommentHidden`/`setRatingHidden`. Add int tests for "mod cannot dismiss a report on own comment" and "mod cannot hide an admin's comment". Phase 8/9: reject `story.authorId === actor.id` (`FEATURED_OWN_STORY`, `CONTEST_OWN_STORY`) for slot creation and placement.

## Finding 2: Hidden review can be revived by deleting and re-rating
- **Severity:** High
- **Location:** Phase 4, "Requirements" (`DELETE /ratings`, `PUT /ratings` upsert) and "Implementation Steps" step 3
- **Flaw:** `deleteRating` removes the row whatever its status ("−1/−score nếu visible" and then delete). The PK is `(user_id, story_id)`, so the next `PUT` inserts a fresh row with `status='visible'`. The plan only keeps the hidden state across *edits*, not across delete + recreate.
- **Failure scenario:** A spammer's review gets reported and mod-hidden. The spammer calls `DELETE /ratings?story=X` and then `PUT /ratings` with the same text, and it is visible again and counted in the totals. The report points at a rating id that no longer exists, so the mod queue context breaks. `hide_rating` stops working as a moderation tool.
- **Evidence:** `packages/db/src/schema/community.ts:79` (PK `ratings_pkey (user_id, story_id)`, so delete frees the slot); plan Phase 4 step 3 handles `hidden_by_mod` only on "sửa", not on delete.
- **Suggested fix:** When a rating is `hidden_by_mod`, `DELETE` should soft-clear it (keep the row and status, null the review) or return `RATING_LOCKED`. `upsertRating` must keep `hidden_by_mod` when a row exists. Add an int test: hide → delete → put → still hidden and not in totals.

## Finding 3: Banning sock-puppets leaves their scores in the public average
- **Severity:** High
- **Location:** Phase 4, "Implementation Steps" step 3, note "[auto] summary lấy count/sum từ cột tổng … lệch nhẹ khi có người bị ban; chấp nhận"
- **Flaw:** `rating_count`/`rating_sum` change only through rating writes and hide/restore. Banning a user doesn't touch them. The plan accepts this as a "slight drift", but drift is exactly what a rating-bomb leaves behind. It also breaks the plan's own rule "mọi danh sách công khai lọc banned" (plan.md "Ban").
- **Failure scenario:** An attacker registers 30 verified accounts (email aliases) and gives a competitor's story 1 star. A mod bans all 30. The reviews disappear, but the average stays at about 1.x with "30+ lượt". The only fix is hiding 30 ratings one by one, and the distribution (filtered) no longer matches the summary (unfiltered).
- **Evidence:** `packages/core/src/moderation/user-status.ts:27-37` (`banUser` updates status/sessions/log/outbox only), `:43-52` (`unbanUser` likewise); plan Phase 4 step 3 note.
- **Suggested fix:** Use one source for the summary. Either compute count/sum/distribution in one `GROUP BY` over `ratings ⋈ users` with `status='visible' AND users.status<>'banned'` (cheap with `ratings_story_id_idx`, so the denormalized columns can go), or adjust the totals of every story the user rated on ban/unban inside `banUser`/`unbanUser`. Add an int test: rate → ban → summary excludes; unban → included again.

## Finding 4: Rankings can be pumped from one IP because per-chapter unique counts are summed
- **Severity:** High
- **Location:** Phase 5, "Requirements" ("Điểm theo truyện = tổng qua mọi chương"), "Risk Assessment" ("Cày view: dựa vào VIEW_RULES hiện có")
- **Flaw:** The score adds up `unique_readers` per chapter per day. Anonymous viewer ids come from a cookie: drop the cookie and you get a fresh id. The 30 s dwell is enforced only on the client. The `/reading/view` endpoint has no rate limit. So one IP can add up to `perIpPerDay` (10) "readers" per chapter per day, multiplied by the chapter count. The plan's choice to sum per chapter is what turns the per-chapter cap into a story-level amplifier. `rising` needs only 20.
- **Failure scenario:** An author publishes 60 short chapters (300 words each) and runs a cookie-less curl loop posting `/api/v1/reading/view` for each chapter 10 times a day from one VPS: 600 "lượt người đọc" a day. The story tops `day`/`rising` and the home "Xếp hạng tuần" top 5 within 15 minutes. That is exactly the "chống bơm view" requirement of spec §6.
- **Evidence:** `packages/shared/src/views.ts:8-11` (per viewer 3, per IP 10, per chapter/day); `packages/api/src/routes/reading.ts:44-49` (missing cookie → fresh anonymous viewer), `:115-121` (`/view` with no `rateLimit`, no server dwell); `packages/core/src/views/record-chapter-view.ts:21-34`.
- **Suggested fix:** Rank on a story-level count that can't be multiplied. For example, keep a per-story-per-day HLL `v:suv:{date}:{storyId}` (added when the view is counted) and store `story_daily_readers`, or cap each story's daily contribution at `max(unique_readers)` across its chapters instead of the sum. Count only signed-in viewers, or cap anonymous ones per IP per story, for `rising`. Add an IP rate limit on `/reading/view`. State the threat model in the phase.

## Finding 5: Ranking and contest pages are never purged, so hidden, banned or newly-18+ stories stay in cached HTML
- **Severity:** High
- **Location:** Phase 5, "Non-functional" ("Cache trang … 10 phút. Không purge."); Phase 9, "Non-functional" ("không purge"); plan.md success criterion "Mọi danh sách công khai mới … không chứa truyện 18+ trong HTML SSR"
- **Flaw:** Purges only cover home, the author page and tag page 1. `LIST_CACHE` is `s-maxage=600, stale-while-revalidate=3600`, so a Cloudflare edge can serve stale HTML for up to about 70 minutes after the last fill. The plan's "≤ 10 phút" claim ignores the SWR window, and `readRanking` filtering at read time doesn't help once the HTML is cached.
- **Failure scenario:** A story with illegal content, or one an author just re-flags `is_mature=true` after a "mislabeled" report, is #1 on `/rankings/week` or a contest entry. A mod hides it or bans the author. The outbox purges home, author and tag pages, but `/rankings/{day,week,month,rising}` and `/contests/{slug}` keep serving the title and cover to guests for up to an hour. That breaks spec §7 ("HTML render phía server của mọi danh sách luôn không chứa truyện 18+") and leaves the takedown incomplete.
- **Evidence:** `packages/core/src/catalog/urls.ts:15-33` (`catalogUrls` returns only home, author and tag paths), `:34-49` (ban: home and tags only); `apps/web/src/lib/cache-headers.ts:16-18` (`LIST_CACHE` with SWR 3600); `packages/core/src/content/hooks.ts:92-106` (every change purges `urlsFor`).
- **Suggested fix:** Phase 5: add the 4 `/rankings/{period}` paths to `catalogUrls` for `story` and `user` changes (a cheap constant list). Phase 9: add `/contests` plus `/contests/{slug}` page 1 for every contest the story has entered (query `contest_entries`). Add `urls-for.int.test.ts` cases. Document the real staleness bound (TTL + SWR).

## Finding 6: `GET /comments/:id/replies` lets anyone with a comment id read replies after the chapter is hidden
- **Severity:** Medium
- **Location:** Phase 1, "Function / Interface Checklist" (`listCommentReplies(db, viewer|null, {commentId, cursor}) → 'COMMENT_NOT_FOUND'`) and "Architecture" (`GET /api/v1/comments/:id/replies?cursor`)
- **Flaw:** The only readability gate, `findReadableChapterRef`, works on `(publicId, number)`. The replies endpoint takes a bare comment UUID, and the plan never says it re-checks that the root is `visible`, that its chapter or story is still readable, or that its author isn't banned. Comment UUIDs are sent to every client in the DTO.
- **Failure scenario:** A chapter gets `hidden_by_mod` for doxxing, and the discussion in its comments is the doxxing. Anyone who saved the root ids (scraper, browser cache) keeps calling `/comments/{id}/replies` and reads the existing thread plus new replies. Replies under a mod-hidden root are also readable, which defeats "gốc bị ẩn → cả nhánh không hiện".
- **Evidence:** `packages/core/src/reader/readable-chapter-ref.ts:17-43` (lookup by `publicId`+`number` only, then `canReadChapter`); plan Phase 1 DTO exposes comment `id`.
- **Suggested fix:** `listCommentReplies` must join root → chapter → story → author and run `canReadChapter`, plus root `status='visible'` and root author not banned. Otherwise return `COMMENT_NOT_FOUND`. Do the same in `deleteComment`, `resolveVisibleTarget` and the paragraph-thread query. Add an int test: hide chapter → replies 404.

## Finding 7: Author-follow notifications push 18+ titles and covers to users who never opted in
- **Severity:** Medium
- **Location:** Phase 3, "Architecture" (fan-out SQL) and "Requirements" (list shows "bìa nhỏ, {Truyện} có chương mới")
- **Flaw:** The fan-out sends to followers of the story *and* of the author, with no `is_mature` or `preferences.showMature` filter. The list also has no such filter. A reader who follows an author for their SFW work, with `showMature` off (or unable to turn it on as a guest-age user), gets notifications showing 18+ story titles and covers. Spec §7 keeps 18+ out of every list surface for users with the pref off.
- **Failure scenario:** User A (showMature=false) follows author B. B starts an `is_mature` story and publishes chapter 1. A's bell shows "1", and `/notifications` renders the 18+ cover and title. Clicking it gives the client-side warning gate, but the cover is already shown.
- **Evidence:** `packages/api/src/routes/stories.ts:38` (lists derive `includeMature` from `getPreferences(...).showMature`, the existing pattern); `apps/web/src/routes/stories.$storyKey.chapter-{$number}.tsx:81` (mature gate is client-side only); plan Phase 3 fan-out SQL filters only `users.status <> 'banned'` and `user_id <> authorId`.
- **Suggested fix:** For `target_type='user'` followers of a mature story, insert only users whose `preferences->>'showMature' = 'true'` (direct story followers chose the page). In `listNotifications`/`countUnreadNotifications`, hide or blur mature items when the viewer's pref is off. Add an int test for both.

## Finding 8: Unverified throwaway accounts can farm follower badges that are never revoked
- **Severity:** Medium
- **Location:** plan.md "Policy cộng đồng" ("Theo dõi chỉ cần đăng nhập"); Phase 7, "Requirements" (`followers_10/100` = count of `follows` to the author; "Huy hiệu đã trao không thu hồi")
- **Flaw:** Sign-in doesn't require a verified email. Sign-up is limited to 5 per IP per hour, so with a few IPs you get hundreds of fake-email accounts a day. Phase 3 lets them follow, Phase 6 counts them as "lượt theo dõi mới", and Phase 7 counts them toward public badges, with no `email_verified` or `status<>'banned'` filter on the follower side. Once awarded, a badge stays even after the sock-puppets are banned.
- **Failure scenario:** An author scripts 100 sign-ups with `@example.invalid` emails across 4 IPs over a day, follows themself, and gets `followers_100`. The badge appears permanently in the SSR author page as social proof. Banning the puppets changes nothing.
- **Evidence:** `packages/auth/src/auth.ts:140` (`requireEmailVerification: false`); `packages/shared/src/rate-limits.ts:48` (signUp 5/hour/IP only); `packages/core/src/policies/user.ts:59-62` (verification is only required for publishing and comments).
- **Suggested fix:** Require `emailVerified` to follow (reuse `requireVerifiedEmail`), or count only verified, non-banned followers in the badge rule and in dashboard totals. Make follower badges revocable, or award them only after N days of follower age. Exclude banned followers in `badgeRuleQuery`.

## Finding 9: The audit-log types don't accept the new targets and actions
- **Severity:** Medium
- **Location:** Phase 1 "Related Code Files" (`setCommentHidden` returns `{type:'comment'}`); Phase 4 (`{type:'rating'}`); Phase 8 "Requirements" (actions `feature_story`/`unfeature_story`); Phase 9 "Requirements" (target_type `contest`, actions `create_contest`/`update_contest`/`set_contest_placement`)
- **Flaw:** `logModerationAction` is typed: `ModerationTarget['type']` is `'story'|'chapter'|'user'|'tag'|'report'`, and `action: ModerationAction` comes from `MODERATION_ACTIONS`. No phase lists `moderation/log-action.ts` as modified, and Phases 8/9 don't list `schemas/reports.ts` for the new action names. Phase 8 only covers the API/core files. The cook will either fail typecheck or reach for an `as` cast and log an unvalidated action. Phase 1 also reports comments by internal UUID, while the existing contract says "by public keys only (internal ids never leave the server)", and nothing in the plan acknowledges the change.
- **Failure scenario:** The Phase 8 cook hits a type error at `logModerationAction(tx, actor, target, 'feature_story', …)` and casts it. The moderation log UI or any `z.enum(MODERATION_ACTIONS)` parser then rejects or mislabels the rows, so the audit trail for featuring is unreadable or silently dropped. That breaks the spec §7 rule "Mọi hành động ghi vào moderation_actions".
- **Evidence:** `packages/core/src/moderation/log-action.ts:8-11` (target union), `:14-20` (`action: ModerationAction`); `packages/shared/src/schemas/reports.ts:24` (`REPORT_TARGET_TYPES`), `:28-40` (`MODERATION_ACTIONS`), `:49-54` (public-keys-only contract).
- **Suggested fix:** Add `packages/core/src/moderation/log-action.ts` to the Related Code Files of Phases 1, 4 and 9 (target types `comment`, `rating`, `contest`; also `featured_slot` if logged per slot), and `packages/shared/src/schemas/reports.ts` `MODERATION_ACTIONS` to Phases 8 and 9. State explicitly that comment and rating report targets use UUIDs, update the comment at `reports.ts:49`, and record the decision in plan.md.
